How it works

Write a task. Get a branch that passed your tests.

Four steps, in the order work actually moves. Everything is a file on disk, so git is the sync layer and there is no database to keep in step.

01

Capture

Dump anything into the inbox — it splits on newlines and files each line. Turn one into a task when you mean it.

02

Dispatch

Each run gets its own git worktree. Tasks declare what blocks them, so an epic starts what is ready and holds the rest.

03

Review

Comment on diff lines, then submit the review with a verdict. Requesting changes resumes the same agent on the same branch, carrying your notes.

04

Land

Approved work enters a merge queue that rebases, runs your named verify steps, and merges. A failure names the step that broke.

The two screens

Capture is one screen. Commitment is another.

Most of what you notice in a day is not work yet. Keeping the two apart is the whole design: nothing you type is a promise until you make it one.

vs. parallel agent runners

Running agents in parallel is the easy half.

Tools like Conductor start several agents in worktrees and show you the diffs. Dispatch does that, and then handles the parts that decide whether the work is worth anything: what to work on, in what order, and how it lands.

agent-runner.md → dispatch.md
@@ what you get @@
parallel agents, each in its own git worktree
a diff you can read when it finishes
-work lives in the tool, not the repo
+tasks are markdown in .dispatch/, synced by git and readable by both of you
-you pick what each agent works on, every time
+tasks declare blockedBy; finishing one unblocks the next automatically
-review means reading a diff and typing a new prompt
+comment on lines, submit a verdict, and the agent resumes with your review attached
-merging is your problem, one branch at a time
+a merge queue rebases, runs your verify steps, and merges — or names the step that failed
-the agent cannot file what it noticed on the way past
+agents get task_save, task_next and dispatch_note over MCP
+Apache 2.0, macOS and Linux, with a CLI and a headless daemon

If you only need several agents going at once, a runner is enough. Dispatch is for when you have more work than you can hold in your head, and you want the finished work to land on its own.

Install

It runs on your machine, against your checkout.

No account, no server, nothing uploaded. The daemon is local and the tracker is a directory in your repo.

macOS

brew install --cask wsoule/tap/dispatch

Signed and notarized. Ships the dispatch CLI on your PATH.
