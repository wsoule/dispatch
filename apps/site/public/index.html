Coding agents don't need another chat window.

They need a tracker. Dispatch is Linear for agents, running on your machine against your checkout: work is markdown in .dispatch/, agents pick up whatever is ready — several at once, each in its own git worktree — and the result lands through a merge queue that runs your tests first.

How it works

Write a task. Get a branch that passed your tests.

Four steps, in the order work actually moves. Everything is a file on disk, so git is the sync layer and there is no database to keep in step.

01

Capture

Dump anything into the inbox — it splits on newlines and files each line. Turn one into a task when you mean it.

02

Dispatch

Each run gets its own git worktree, so several go at once. Working an epic starts everything that is ready up to your concurrency cap, and holds the rest until a slot frees.

03

Review

Comment on diff lines, then submit the review with a verdict. Requesting changes resumes the same agent on the same branch, carrying your notes.

04

Land

Approved work enters a merge queue that rebases, runs your named verify steps, and merges. A failure names the step that broke.

One lane per epic, the same status columns repeated down the page. It answers “which epic is stuck”, which a single flat board cannot. Work a whole lane and three runs open at once, each in its own worktree, with the fourth held until one finishes — the cap is orchestrator.epicConcurrency, and it exists so a twelve-task epic does not open twelve worktrees. The kind badges, the split into lines and the grouping hint are the app's own functions running here, not a script that imitates them — a demo you can poke is only worth anything if poking it tells you the truth.

vs. chat-first harnesses

The work is not a conversation.

Almost every agent tool makes the chat the unit of work. So what you decided lives in scrollback, the next session starts by re-explaining it, and nothing knows what to do next but you. Running several agents at once — the thing the newer tools add — makes that worse, not better: now there are four conversations to hold.

chat-first.md → dispatch.md
an agent that reads and edits your repo
a diff you can read when it finishes
-the unit of work is a conversation
+the unit of work is a task file, in git, readable by both of you
-what you decided lives in scrollback
+it lives in .dispatch/, so it survives the session and shows up in review
-every session starts by re-explaining
+task_next hands over the next ready task; task_save and dispatch_note let the agent file what it noticed on the way past
-you decide what to work on, every time
+tasks declare blockedBy; finishing one unblocks the next automatically
-review means reading a diff and typing a new prompt
+comment on lines, submit a verdict, and the agent resumes with your review attached
-merging is your problem, one branch at a time
+a merge queue rebases, runs your verify steps, and merges — or names the step that failed
+Apache 2.0, macOS and Linux, with a CLI and a headless daemon

Tools like Conductor already run several agents in parallel worktrees and show you the diffs, and that part is genuinely the easy half. Dispatch does it too — and then handles what decides whether the work was worth anything: what to pick up, in what order, and how it lands.

Install

It runs on your machine, against your checkout.

No account, no server, nothing uploaded. The daemon is local and the tracker is a directory in your repo.

macOS

brew install --cask wsoule/tap/dispatch

Signed and notarized. Ships the dispatch CLI on your PATH.
