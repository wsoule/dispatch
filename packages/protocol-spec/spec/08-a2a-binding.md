# 8 A2A binding

This section binds DMP to [A2A](https://a2a-protocol.org) 1.0. A host that
implements it serves one A2A agent to A2A clients over A2A's HTTP+JSON binding,
and may send messages to A2A agents of its own choosing, its peers. A2A's terms
(agent card, `Task`, `Message`, `Part`, `Artifact`, `contextId`, the
`TASK_STATE_*` names) keep A2A's meaning; the A2A specification is normative for
everything this section does not say.

The requirements here on A2A's own wire (the card, the HTTP binding, streams and
errors) are attested by a run of the A2A TCK ([§8.10](08-a2a-binding.md#s8.10),
[§12.1](12-conformance.md#s12.1)). The requirements on DMP messages are tested
by the `a2a-binding` vectors each subsection names. An A2A client and an A2A
peer are external ([§2.1](02-terminology.md#s2.1)): a host that implements this
binding classifies their addresses, and every rule of this document for external
senders and recipients applies to them.

## 8.1 Agent and skills

A host serves one agent card per project: one set of addresses behind one DMP
host is one A2A agent. The card is served without authentication at
`/.well-known/agent-card.json` on the root of the host's A2A listener (A2A
§8.2), and names an interface with `protocolBinding` `HTTP+JSON` and
`protocolVersion` `1.0`.

- **Extensions.** The card declares the three extensions of
  [§8.4](08-a2a-binding.md#s8.4) to [§8.6](08-a2a-binding.md#s8.6) in
  `capabilities.extensions`, each with `required: false`, so a client that knows
  none of them never meets `ExtensionSupportRequiredError` and reads the same
  facts as plain text in `status.message`.
- **Security.** The card declares one HTTP bearer scheme. Each client has its
  own token, which the host honors only once a deciding principal has approved
  the client's registration ([§9.1](09-identity-and-authorization.md#s9.1)). A
  client sends as one `agent:` address; the Dispatch profile names clients
  `agent:<requester>/a2a.<name>` and reserves the `a2a.` prefix, so no other
  agent can register a name that passes for a client.
- **Skills.** `ask` asks the host's owner ([§2.3](02-terminology.md#s2.3)) a
  question; an answer can take hours, so a client sends with `returnImmediately`
  and then streams, subscribes or polls. `handoff` proposes a unit of work with
  `work/v1` ([§8.6](08-a2a-binding.md#s8.6)), which a deciding principal
  approves before anything runs. `status` reports the state of the client's own
  handoffs. A host that does not take handoffs omits the `handoff` skill and
  refuses a handoff request as `invalid` on `work.skill`.
- **Privacy.** The card MUST NOT name the host's members, its owner's handle,
  counts of its work items or any internal URL. The ask skill's description
  states the host's bound on a blocking send ([§8.10](08-a2a-binding.md#s8.10)).

## 8.2 Mapping

| DMP                                                          | A2A 1.0                                                                | Rule                                                                                                                                 |
| ------------------------------------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| a project (one host)                                         | one agent card                                                         | skills `ask`, `handoff`, `status` ([§8.1](08-a2a-binding.md#s8.1))                                                                   |
| the message that opens an exchange                           | a `Task`; `Task.id` is that message's id                               | ids are generated by the host; clients treat them as opaque strings                                                                  |
| `thread`                                                     | `contextId`                                                            | a client's `contextId` must name a thread the client takes part in; any other is refused, never replaced (A2A §3.4.1)                |
| `body`                                                       | text parts                                                             | inbound text parts are joined with a blank line; outbound text is `text/markdown`, or `text/plain` when the client accepts only that |
| `data`                                                       | one data part (`application/json`)                                     | inbound data is stored wrapped ([§8.8](08-a2a-binding.md#s8.8)) and unwrapped when it goes back to the client that sent it           |
| `from`, `to`, `kind`, `replyTo`, `choices`, `choice`, `refs` | `envelope/v1` ([§8.4](08-a2a-binding.md#s8.4))                         | without it, `to` is the owner and the kind follows the skill                                                                         |
| `idempotencyKey` ([§4.9](04-messages.md#s4.9))               | the client's `messageId`                                               | required: one line of at most 200 bytes, so a retried request replays                                                                |
| a blocking question to the client                            | `TASK_STATE_INPUT_REQUIRED`, the question in `status.message`          | the client answers with a message carrying that `taskId`                                                                             |
| an open gate that concerns the task                          | `TASK_STATE_AUTH_REQUIRED`, `gate/v1` ([§8.5](08-a2a-binding.md#s8.5)) | never answerable by the client                                                                                                       |
| a handoff                                                    | a `Task` that moves through `work/v1`'s lifecycle                      | [§8.6](08-a2a-binding.md#s8.6), [§8.7](08-a2a-binding.md#s8.7)                                                                       |
| results                                                      | `Artifact`s: `answer`, and `work/v1`'s `pr`, `diffstat`, `evidence`    | nothing else ([§8.8](08-a2a-binding.md#s8.8))                                                                                        |
| deliveries, channels, wake, mute                             | none                                                                   | they stay inside the host; a client's `urgent` and wake request are refused ([§8.4](08-a2a-binding.md#s8.4))                         |
| a recipient `a2a:<alias>`                                    | one `SendMessage` to that peer per message                             | [§8.9](08-a2a-binding.md#s8.9)                                                                                                       |

**Parts.** URL parts (at most 20, each at most 2 KiB) are appended to the body
as markdown links, one per line; the host never fetches them. A raw (bytes) part
is refused with `ContentTypeNotSupportedError`. All the metadata of one message
together is at most 64 KiB ([§8.3](08-a2a-binding.md#s8.3)), and the host caps a
request body at 256 KiB; DMP's limits of [§4.5](04-messages.md#s4.5) then apply
to the message a request becomes.

**States.** A failed session never makes a task `TASK_STATE_FAILED`, because the
work item resumes. `TASK_STATE_UNSPECIFIED` is never sent. A task's state is
decided by [§8.7](08-a2a-binding.md#s8.7).

**Errors.** A host maps the errors of [§10](10-errors.md#s10) onto A2A's
(`google.rpc.Status` carrying a `google.rpc.ErrorInfo`; A2A §11.6), with the
same answer for an absent target and one the client may not see
([§13.5](13-security-and-privacy.md#s13.5)):

| DMP error                                              | A2A response                                                                                                                 |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `invalid` on a field                                   | 400 `INVALID_ARGUMENT` with a `google.rpc.BadRequest` naming the A2A path of the field (`body` is `message.parts`)           |
| `forbidden` or `not-found` on the task                 | 404 `TASK_NOT_FOUND`, the same for both                                                                                      |
| `forbidden` or `not-found` on `contextId`              | 400 `INVALID_ARGUMENT` on `message.contextId`, "unknown contextId", the same for both                                        |
| `forbidden` or `not-found` on `replyTo` or `refs[i]`   | 400 `INVALID_ARGUMENT` on that field, "unknown message", the same for both                                                   |
| `not-found` on `to[i]`                                 | 400 `INVALID_ARGUMENT` on that field                                                                                         |
| `forbidden` on `to[i]`, `urgent`, `wake` or `kind`     | 403 `PERMISSION_DENIED`, with the reason `FORBIDDEN_ADDRESS`, `URGENT_NOT_ALLOWED`, `WAKE_NOT_ALLOWED` or `KIND_NOT_ALLOWED` |
| `conflict`, or a message to a task in a terminal state | 400 `UNSUPPORTED_OPERATION`                                                                                                  |
| `limited`                                              | 429 `RESOURCE_EXHAUSTED` with `Retry-After`                                                                                  |

A missing or unknown bearer is 401 with `WWW-Authenticate: Bearer`, and the host
gives one answer for every bearer that is not a client's own, so its public port
cannot confirm that some other token of the host is valid.

## 8.3 Extension activation and placement

The three extensions carry what A2A 1.0 has no field for: DMP addressing, why a
task is waiting on its owner, and handoffs of work. Each extension URI serves
its own subsection together with this one.

An extension is active for a request when its URI appears in the
`A2A-Extensions` header or in `message.extensions`. The response echoes the
active URIs in `A2A-Extensions`, and a host MUST write extension metadata only
for active extensions. A client that activates none gets the same facts as plain
text in `status.message`.

Extension data sits in `metadata[<URI>]`. On a `Message` (including
`status.message`) and on an `Artifact`, the object's `extensions` list also
names the URI. A `Task` has no `extensions` field, so task-level data lives only
in `Task.metadata[<URI>]`, written when the request activated the extension.

All metadata on one message together MUST be at most 64 KiB as JSON; a host
refuses more as `invalid` on `message.metadata`. The extensions fit well inside
it: `work/v1` tops out near 36 KB and `envelope/v1` near 15 KB with inbound refs
restricted as [§8.4](08-a2a-binding.md#s8.4) says. Body (64 KiB), data (64 KiB),
metadata (64 KiB) and A2A's framing fit a 256 KiB request. Vectors:
`a2a.envelope-ext.refuses-metadata-over-64-kib`.

Each extension is versioned by its URI: a breaking change mints a new URI ending
`/v2` ([§14.4](14-versioning.md#s14.4)). The registry of extension URIs is
[§11.10](11-registries.md#s11.10).

## 8.4 envelope/v1

`https://dispatch.foo/a2a/ext/envelope/v1` is a profile on `Message.metadata`: a
DMP envelope ([§4.1](04-messages.md#s4.1)) riding on an A2A message.

```ts
interface EnvelopeExtV1 {
  id?: string; // host to client: the DMP message id
  thread?: string; // host to client: the DMP thread id
  from?: string; // host to client: the sender's address; ignored inbound
  to?: string[]; // client to host only: recipients (default: the owner)
  kind?: 'message' | 'question' | 'answer' | 'handoff' | 'notice';
  replyTo?: string; // a DMP message id the caller takes part in
  blocking?: boolean; // questions only; a client's question always blocks
  choices?: string[]; // at most 20, each one line of at most 200 bytes
  choice?: string; // answers only; one of the question's choices
  refs?: { type: string; id: string }[]; // inbound: at most 50, task and message ids only
  urgent?: boolean; // inbound true is refused
  wake?: 'none' | 'request'; // inbound 'request' is refused
}
```

**Inbound.** A host reads a client's envelope before anything else of the
message, and MUST apply these rules on top of [§4.5](04-messages.md#s4.5):

- `from`, `id` and `thread` are ignored: the bearer decides who sends, and the
  host assigns the id and the thread.
- `urgent: true` is refused as `forbidden` on `urgent`, and `wake: 'request'` as
  `forbidden` on `wake`: a client may not jump a mailbox or start a session.
- An `x-` kind is refused as `forbidden` on `kind`, so a client cannot put an
  uninterpreted kind in front of a human; any other kind outside the list above
  is `invalid` on `kind`.
- A message without a `taskId` opens a task, and is never an `answer` or a
  `handoff`: either kind is `invalid` on `kind`. A client answers a question put
  to it by continuing the task that asks it, with that task's `taskId`
  ([§8.2](08-a2a-binding.md#s8.2)), and proposes work with `work/v1`
  ([§8.6](08-a2a-binding.md#s8.6)). Of a continuation's envelope only `choice`
  and `refs` count.
- Each `to` entry is one line of at most 512 bytes, at most 50 of them; each
  choice and the choice are one line of at most 200 bytes, at most 20 choices;
  `blocking` is a boolean. A violation is `invalid` on the field or its slot.
- A client may address only the humans on its recipient list, which is the owner
  unless a deciding principal named others when approving the client, and the
  work items of its own approved handoffs. Anything else is `forbidden` on
  `to[i]`, the same for a member of the host and a stranger, so the answer tells
  a client nothing about who exists.
- Refs name only `task` and `message` ids the client may already see: its own
  tasks and the messages in their scope ([§8.7](08-a2a-binding.md#s8.7)), and
  the work items of its approved handoffs. A ref that is not an object is
  `invalid` on `refs[i]`; one of another type is `invalid` on `refs[i].type`,
  one that carries an `at` on `refs[i].at`, and one whose `id` is not one line
  of at most 512 bytes on `refs[i].id`. An id the client may not see is
  `not-found` on `refs[i]`, as an absent one is.
- Without an envelope, the message is a blocking question to the owner.

Vectors: `a2a.envelope-ext.accepts-recipients-choices-and-message-refs`,
`a2a.envelope-ext.accepts-no-envelope`, `a2a.envelope-ext.refuses-urgent`,
`a2a.envelope-ext.refuses-a-wake-request`,
`a2a.envelope-ext.refuses-a-private-use-kind`,
`a2a.envelope-ext.refuses-an-unknown-kind`,
`a2a.envelope-ext.refuses-a-bad-recipient`,
`a2a.envelope-ext.refuses-a-ref-type-other-than-task-or-message`,
`a2a.envelope-ext.refuses-a-ref-anchor`,
`a2a.envelope-ext.refuses-more-than-20-choices`,
`a2a.envelope-ext.refuses-a-choice-over-200-bytes`,
`a2a.envelope-ext.refuses-blocking-that-is-not-a-boolean`,
`a2a.external.the-host-sets-id-thread-and-from`,
`a2a.external.defaults-to-a-blocking-question-to-the-owner`,
`a2a.external.a-client-reaches-only-the-owner`,
`a2a.external.an-opening-answer-or-handoff-is-refused`,
`a2a.external.an-answer-from-a-client-is-never-a-close`.

**Outbound.** A host MUST NOT write `to` to a client. To a peer it writes only
the peer's own address, so no other recipient leaves the host. Refs are written
as the DMP sender wrote them, as opaque strings.

**External data** is stored wrapped under this URI, as
`{ "https://dispatch.foo/a2a/ext/envelope/v1": <value> }`, so it has no
top-level `type` ([§8.8](08-a2a-binding.md#s8.8)); it is unwrapped when it goes
back to the client that sent it.

## 8.5 gate/v1

`https://dispatch.foo/a2a/ext/gate/v1` is data only, and read only: it rides on
`status.message.metadata` while a task is `TASK_STATE_AUTH_REQUIRED`
([§8.7](08-a2a-binding.md#s8.7)), and says which gates hold the task open.

```ts
interface GateStateV1 {
  gates: {
    id: string; // the gate's DMP message id
    type: string; // the gate's type (§5.6)
    openedAt: string; // ISO 8601
    waitingOn: 'owner';
  }[];
}
```

Only a deciding principal answers a gate, and a client never can
([§5.2](05-gates.md#s5.2)). A gate's data never leaves the host
([§5.8](05-gates.md#s5.8)): a `tool-approval` gate quotes a tool's input and a
`scope` gate names paths. Only each gate's id, type and time leave, here, and
`status.message` carries one fixed sentence per type in place of the gate's
body. The Dispatch profile's sentences:

- `task-proposal`: "Waiting for the project owner to approve this handoff."
- `tool-approval`: "Waiting for the project owner to approve a tool call."
- `scope`: "Waiting for the project owner to approve a change of scope."
- `wake`: "Waiting for the project owner to approve waking the task."

Vectors: `a2a.projection.row-8-an-open-gate-needs-authorization`,
`a2a.projection.row-8-gate-v1-lists-id-type-and-time`,
`a2a.egress.gate-data-never-reaches-a-client`,
`a2a.egress.a-reply-to-a-gate-never-reaches-a-client`.

## 8.6 work/v1

`https://dispatch.foo/a2a/ext/work/v1` is a profile plus a sub-state of
`TASK_STATE_WORKING`. It is registered as provisional
([§11.10](11-registries.md#s11.10)) until the `task-proposal` gate it relies on
is permanent, and until then no vector tests it.

A client sends a request on `Message.metadata`; it selects the skill, and its
absence means `ask`:

```ts
type WorkRequestV1 =
  | {
      skill: 'handoff';
      title: string; // required; one line, at most 200 bytes
      acceptance?: string[]; // at most 20 entries, each one line of at most 500 bytes
      writes?: string[]; // at most 50 repo-relative paths or globs, each at most 512 bytes
      priority?: 'urgent' | 'high' | 'medium' | 'low' | 'none'; // capped at 'medium'
      labels?: string[]; // at most 10, each at most 50 bytes
    }
  | { skill: 'status'; task?: string }; // an A2A task id; absent means all of the caller's
```

A host MUST refuse a request that breaks these limits as `invalid` on the field
or its slot, under `work.` (`work.title`, `work.writes[1]`). Lengths are UTF-8
bytes. A write is relative to the repository: an absolute path, a drive letter,
a backslash or a `..` segment is refused.

**Handoffs.** A handoff becomes a draft work item that a deciding principal
approves before anything runs. The host raises a `task-proposal` gate for it
([§11.6](11-registries.md#s11.6)): only the system address raises one, its
choices are `approve` and `decline`, and its data names the drafted work item,
the client that proposed it and the handoff message. Approving it promotes the
draft; declining it drops the draft. A handoff starts at the host's highest
risk, so none of its own gates decides itself; a client chooses no risk, its
priority is capped at `medium`, and its labels are stored under an `a2a/`
prefix.

The host tells the client its handoff's state on `Task.metadata` and on
`status.message.metadata`:

```ts
interface WorkStateV1 {
  task: string; // the DMP work item id
  title: string;
  status: string; // draft, ready, working, review, landing, landed, dropped, or a host's own
  stage?: 'review' | 'landing'; // the TASK_STATE_WORKING sub-state
}
```

Results go on `Artifact.metadata`, and an artifact's `artifactId` equals its
`kind`:

```ts
type WorkArtifactV1 =
  | { kind: 'answer'; messageId: string; choice?: string }
  | { kind: 'pr'; url: string; number: number; state?: 'open' | 'merged' }
  | {
      kind: 'diffstat';
      files: number;
      insertions: number;
      deletions: number;
      perFile: { path: string; insertions: number; deletions: number }[]; // at most 200
    }
  | {
      kind: 'evidence';
      items: {
        command: string;
        exitCode: number;
        durationMs: number;
        summary: string;
      }[]; // at most 50
    };
```

Each artifact is at most 64 KiB as JSON; past that, `perFile` and `items` are
cut to fit and `metadata.truncated` is `true`. There is no branch artifact:
branch names and commit ids do not leave the host
([§8.8](08-a2a-binding.md#s8.8)).

## 8.7 Task-state projection

A host decides a task's state from the facts it holds, and MUST report the state
of the first row that matches. The same decision drives every read of a task:
GetTask, ListTasks and every stream event.

| #   | Condition                                                                                                                    | State                                             | `status.message`                                                          |
| --- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------- |
| 1   | the client canceled the task                                                                                                 | `CANCELED`                                        | "Canceled by the client."                                                 |
| 2   | a handoff whose proposal was declined, or whose work item was dropped by anyone but the client; or an ask the owner declined | `REJECTED`                                        | the decline or drop, with any note                                        |
| 3   | an ask whose root the system address closed ([§4.8](04-messages.md#s4.8)), or whose recipient work item was dropped          | `FAILED`                                          | the reason                                                                |
| 4   | a handoff whose work item no longer exists                                                                                   | `FAILED`                                          | "The task was deleted."                                                   |
| 5   | an ask whose root has an answer                                                                                              | `COMPLETED`                                       | the answer, and the `answer` artifact                                     |
| 6   | a handoff whose work item is `landed`                                                                                        | `COMPLETED`                                       | "Landed.", and the work artifacts                                         |
| 7   | an open blocking question to the client, in scope, that has no gate data and replies to no message that has gate data        | `INPUT_REQUIRED`                                  | the oldest such question                                                  |
| 8   | an open gate in scope                                                                                                        | `AUTH_REQUIRED`                                   | the gate's fixed sentence, and `gate/v1` ([§8.5](08-a2a-binding.md#s8.5)) |
| 9   | a handoff whose work item is `working`, `review`, `landing` or a status of the host's own                                    | `WORKING`, with the `stage` `review` or `landing` | the latest in-scope message not from the client, else "Working."          |
| 10  | a handoff whose work item is `draft` or `ready` after approval                                                               | `SUBMITTED`                                       | "Approved; waiting to be scheduled."                                      |
| 11  | an ask whose root deliveries are all `held`                                                                                  | `SUBMITTED`                                       | a sentence naming the mailbox the ask waits in                            |
| 12  | otherwise                                                                                                                    | `WORKING`                                         | the latest in-scope message not from the client, else "Working."          |

Row 3 reads a close only from the system address, as every host reads the system
markers ([§13.14](13-security-and-privacy.md#s13.14)): the same data from any
other sender is an answer, and row 5 matches. Row 7 tests gate data with the
rule of [§5.8](05-gates.md#s5.8), on the question and on the message it replies
to, whatever the gate's type and whether or not the host knows it: a gate, or an
answer to one, never strands a client in `INPUT_REQUIRED` with nothing it may
answer. A host already refuses to send such a question to a client
([§8.8](08-a2a-binding.md#s8.8)); row 7 also covers rows an older host stored.
The fixed sentences are the Dispatch profile's and are not normative.

`a2a.projection.row-11-needs-every-root-delivery-held`,

**Scope.** A task's scope is every message that is both related to the task and
visible to the client:

- **related**: the task's root; every message whose `replyTo` chain reaches the
  root; and, for an approved handoff, every message between the client and the
  handoff's work item (from the client to `task:<id>`, or from that work item or
  one of its sessions to the client);
- **visible**: sent by the client, or carrying a delivery whose recipient is the
  client. This is the read rule of [§9.3](09-identity-and-authorization.md#s9.3)
  for a principal that does not decide.

A member's reply to the owner inside the ask's thread, the owner's answer to a
gate and the gate itself therefore never reach the client, in history, in
`status.message` or in a stream. Besides in-scope messages, the only text in
`status.message` is the host's fixed sentences.

A gate is **in scope** when it concerns the task: the task's own `task-proposal`
gate, or a gate about the handoff's work item or one of its sessions. The
Dispatch profile counts a `tool-approval` gate of one of the work item's
sessions, a `scope` gate one of them raised, and a `wake` gate whose target is
the work item. Only the gate's id, type and time leave
([§8.5](08-a2a-binding.md#s8.5)); the gate message is never in scope.

## 8.8 External senders

A host that implements this binding classifies each address it reaches through
it as a `client` or a `peer`, and decides for every external recipient of a send
whether to deliver to it, skip it or refuse the send
([§2.1](02-terminology.md#s2.1)). A direct recipient it refuses fails the send
with that error; a recipient reached through a channel that it refuses is
skipped, as a session that is not live is when a channel reaches it
([§3.5](03-addresses.md#s3.5)). Which recipients it admits is the host's own
policy; the vectors script a host that admits every one
([§12.4.2](12-conformance.md#s12.4.2)) and check that the decision is asked for.
Vectors: `a2a.egress.plain-mail-to-a-client-is-admitted-by-the-host`.

**Gate data never goes external.** A send in which the message, or the message
it replies to, has gate data ([§5.1](05-gates.md#s5.1)) while any resolved
recipient is external MUST fail as `forbidden` on `data` before anything is
stored, as [§5.8](05-gates.md#s5.8) says, whoever sends it and whatever other
recipients it has. Vectors: `a2a.egress.gate-data-never-reaches-a-client`,
`a2a.egress.a-gate-with-a-local-recipient-is-refused-whole`,
`a2a.egress.a-reply-to-a-gate-never-reaches-a-client`.

**Inbound content.** What a client or a peer sends becomes a send input only
through these rules:

- **Data is wrapped.** All external data is stored as
  `{ "https://dispatch.foo/a2a/ext/envelope/v1": <value> }`, where the value is
  the single data part, or an array of the parts when there are several. It has
  no top-level `type`, so it can never be gate data, `x-closed` or `x-breaker`,
  whatever the sender writes. If the wrapped value exceeds 64 KiB, it is dropped
  and the body ends with "(data part over 64 KiB omitted)".
- **Bodies.** A client's body over 64 KiB is refused as `invalid` on `body`,
  since the client can fix it; a peer's is cut to fit and ends with "[…
  truncated by Dispatch]". A body with no text becomes "(no text)" when the
  message has data; a client's message with neither is refused as `invalid` on
  `body`.
- **Choices** a peer offers are trimmed, joined onto one line, deduplicated,
  limited to 200 bytes each and to the first 20; the rest are dropped, and a
  question left with none has no choices. A client's choices are validated as
  [§8.4](08-a2a-binding.md#s8.4) says.
- **Refs** from a client follow [§8.4](08-a2a-binding.md#s8.4); a peer's refs
  are dropped, since its ids mean nothing to this host.

Vectors: `a2a.external.gate-shaped-data-is-wrapped`,
`a2a.external.several-data-parts-become-one-array`,
`a2a.external.an-empty-message-is-refused`,
`a2a.external.data-alone-reads-no-text`.

**Never the system address.** A message from a client is sent as the client's
own address, and one recorded from a peer as the peer's `a2a:` address
([§8.9](08-a2a-binding.md#s8.9)); neither decides
([§9.2](09-identity-and-authorization.md#s9.2)). Whatever an envelope names as
`from`, an external sender MUST NOT become the system address, and a close or a
marker it sends never reads as one ([§13.1](13-security-and-privacy.md#s13.1),
[§13.14](13-security-and-privacy.md#s13.14)). Vectors:
`a2a.external.never-speaks-as-the-system`,
`a2a.external.an-answer-from-a-client-is-never-a-close`.

**Presenting.** A host marks an external sender's message wherever it puts one
in a model's context, and quotes every line that carries the sender's text, as
[§6.8](06-delivery.md#s6.8) says; a body that imitates the host's header or a
host line stays inside quoted lines. Vectors:
`a2a.external.a-clients-question-is-quoted-when-pushed`,
`a2a.external.a-forged-header-stays-quoted`,
`a2a.external.a-clients-digest-starts-with-host-text`.

**What leaves.** Besides gate data, a host implementing this binding MUST NOT
send through it anything in the right-hand column below; the left-hand column is
all it sends of its own accord ([§13.9](13-security-and-privacy.md#s13.9)). A
host cannot vet what a human or an agent chooses to write into a message
addressed to a client or a peer, or into an evidence `summary`, which is free
text a session writes; it marks external recipients in its agents' tools and in
rendered headers so they know.

| Exported                                                                                                                                                                                                                                                                                                                                                                          | Never exported                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| in-scope messages ([§8.7](08-a2a-binding.md#s8.7)): their body, data, refs as opaque strings, choices and sender address; a task's state and stage; a handoff's title; the `answer`, `pr`, `diffstat` (paths and counts) and `evidence` (command, exit code, duration, summary) artifacts; to a peer, the envelope of each message addressed to it, with `to` reduced to the peer | gate data and gate messages; messages the client neither sent nor received, and other threads; the other recipients of a message; branch names and commit ids; session logs, transcripts and diff contents; file contents and attachments; memory entries; documents; ledger entries; review findings; the host's member list (addressing a `human:` depends on the client's recipient list, not on membership); the owner's handle on the card; work items other than the client's own |

## 8.9 Outbound peers

This subsection is provisional: the scheme `a2a` is registered as provisional
([§11.1](11-registries.md#s11.1)), and no vector tests it yet.

A peer is another A2A agent the host sends to, addressed as `a2a:<alias>`. The
alias follows the handle grammar of [§3.1](03-addresses.md#s3.1)
(`[a-z0-9][a-z0-9._-]*`), at most 40 characters. An `a2a:` address is valid in
`to` and as a channel member; it is `from` only on a message the host records
from that peer, which never decides. No principal ever sends as one.

**Adding a peer.** Only a deciding principal adds a peer, by naming its card's
URL. The host then:

1. fetches the card over `https:` (plain `http:` only when the host's operator
   allows it), following no redirect, within 10 s and 256 KiB;
2. picks the card's first interface with `protocolVersion` 1.0 over `HTTP+JSON`
   or `JSONRPC`, and refuses a peer that offers neither;
3. requires the interface's origin to equal the card's, unless the operator
   confirms the difference, so a hostile card cannot point the host at a service
   inside its network;
4. requires a security scheme the host can satisfy with a bearer token or an API
   key in a header; and
5. keeps the credential apart from the host's messages and configuration.

A URL that a principal other than the host's operator supplies MUST pass a
public-URL check before every fetch: `https:` only, no user information and no
IP literal host, and no address that resolves to a loopback, private,
link-local, shared (`100.64.0.0/10`), multicast or unspecified range, or an
IPv4-mapped form of one. The card's name, description and skills are shown to
humans and sessions as quoted, untrusted text. The host refreshes the card
daily; a refresh that changes the interface's origin disables the peer, and a
401 or 403 from the peer marks it failed, each with one notice to the owner.

**Sending.** Only an active peer receives mail. A direct send to a peer that is
absent or inactive fails as `not-found` on `to[i]`; a channel member that is an
inactive peer is skipped, with at most one notice a day to the owner. A direct
send over the host's per-peer hourly quota fails as `limited` on `to[i]` and
stores nothing; a channel delivery over it waits. The host's own system sends
never address a peer, and only a deciding principal may make a peer a member of
a channel, since every later message to the channel would then leave the host.

A delivery to a peer is held ([§6.2](06-delivery.md#s6.2)), and the host relays
it outside the send, so a sender never waits on the network. For each delivery
the host sends one `SendMessage` with `returnImmediately`, whose `messageId` is
the DMP message id (so a peer that deduplicates never processes a retry twice),
whose parts are the body and the data, and whose `envelope/v1` carries `from`,
`to` reduced to the peer, `kind`, `replyTo`, `choices`, `choice` and `refs`. A
handoff to a peer also carries `work/v1` with the handoff's first line as its
title. On acceptance the delivery moves from `held` to `pushed`. A network error
or a 5xx is retried with backoff; after 24 hours the host gives up, closing a
question and sending the sender of any other kind a notice. A 4xx is not
retried: the sender gets the peer's error as a notice, and a question is closed.

**Replies.** The host follows each open task of a peer, by stream or by polling,
and records each peer event as at most one message from the peer, through the
inbound rules of [§8.8](08-a2a-binding.md#s8.8), with an idempotency key made
from the peer's task id, its state and the event's message id or time, so a
replay or a reconnect never records it twice:

| Peer's task                      | Recorded in the thread                                                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| a direct `Message` response      | an `answer` to a question addressed to the peer directly; otherwise a `message` reply                                                   |
| `COMPLETED`                      | for a question addressed to the peer directly, an `answer` with the status text and artifacts; otherwise a `notice` reply with the same |
| `INPUT_REQUIRED`                 | a blocking `question` from the peer to the original sender; its answer goes back to the peer's task                                     |
| `AUTH_REQUIRED`                  | a `notice` to the sender that the peer waits on its own authorization                                                                   |
| a `WORKING` status message       | a `notice` reply, at most one a minute                                                                                                  |
| `FAILED`, `REJECTED`, `CANCELED` | a question addressed to the peer directly is closed with the peer's reason; otherwise a `notice`                                        |
| no terminal state after 7 days   | a question is closed                                                                                                                    |

A peer answers only a plain question addressed to it directly. It never answers
a gate, since gate data never reaches it, and its reply to a question it
received through a channel is recorded as a `message`, because one member's
answer would close the question for every member. A handoff to a peer is closed
by the system address when the peer first reports a decisive state (`WORKING`,
`COMPLETED` or `REJECTED`); later states and the peer's artifacts arrive as
notices. Messages from peers count as agent turns for the breaker
([§6.6](06-delivery.md#s6.6)), so a session and a peer cannot answer each other
forever.

## 8.10 Declared deviations

An A2A binding claim needs an attested run of the A2A TCK
([§12.1](12-conformance.md#s12.1)) at commit
`263b9cfaf16a554bdfb166a7ba5b67716e946349`, over HTTP+JSON, at its MUST level.
The run passes when every failure is one of these two deviations, which this
binding declares on purpose; any other fails the claim
([§12.6](12-conformance.md#s12.6)):

- **`bounded-blocking-wait`**, a MUST deviation from A2A §3.2.2 (the TCK's
  `CORE-EXECUTION-MODE-001`). A `SendMessage` without `returnImmediately` waits
  until the task is terminal, `INPUT_REQUIRED` or `AUTH_REQUIRED`, or until the
  host's bound passes, and then returns the task as it stands. An answer from a
  person can take hours, and tunnels and proxies cut idle requests long before
  that. The ask skill's description on the card states the bound
  ([§8.1](08-a2a-binding.md#s8.1)); the Dispatch profile waits 60 seconds by
  default and at most 600. A green TCK run says nothing about this deviation,
  since the TCK's scenarios finish inside any bound, so a host tests it on its
  own.
- **`application-json`**, a SHOULD deviation from A2A §11.1. Responses are
  `application/json`, which the pinned TCK's `HTTP_JSON-SVC-001` requires, not
  the `application/a2a+json` that A2A §11.1 recommends; requests may use either.

Refusing a `contextId` the client does not take part in is not a deviation: A2A
§3.4.1 lets an agent reject a `contextId` it cannot accept, and this binding
never replaces one ([§8.2](08-a2a-binding.md#s8.2)). A TCK scenario that expects
the other behavior allowed there fails against such a host, so Dispatch attests
its TCK run against a test subject that keeps a client's `contextId`, which
§3.4.1 also allows.
